# 提出書類AIアシスタント（クリック体験用モック）

専門工事会社（電気工事・空調・配管・足場・塗装・防水・内装・設備工事など）向けに、
**会社情報・作業員情報・資格証を一度登録するだけで、現場ごとに必要な提出書類と不足情報を把握し、提出用データを準備できる**
というコンセプトを検証するための、クリック操作可能な画面モックです。

**本番システムではありません。** 実際のデータ保存・AI/OCR処理・メール送信・外部サービス（GreenSite / Buildee 等）連携は一切行われません。
すべてブラウザの `localStorage` 内で完結する疑似データ・疑似処理です。

---

## 起動方法

ビルド不要・依存パッケージ不要の素のHTML/CSS/JavaScriptです。

**方法A：ローカルサーバーで開く（推奨）**

```bash
# このフォルダで実行
python -m http.server 8080
# または
npx serve .
```

ブラウザで `http://localhost:8080/index.html` を開いてください。

**方法B：ファイルを直接開く**

`index.html` をブラウザにドラッグ＆ドロップ、またはダブルクリックでも動作します
（`file://` で開いた場合も `localStorage` は正常に機能しますが、環境によっては
ブラウザのセキュリティ設定により制限される場合があるため、方法Aを推奨します）。

対応ブラウザ：最新版の Chrome / Edge を推奨。

## セルフガイドデモ（3分デモ）

営業担当・説明担当が同席しなくても、初めて訪れた専門工事会社の方が
「不足確認 → 依頼 → 提出 → 登録 → 解消 → 提出準備」という一連の価値を、
実際の画面を操作しながら約2分30秒〜4分で体験できるガイド付きモードです。
設計意図・完了条件・イベント一覧の詳細は [`DEMO_SPEC.md`](DEMO_SPEC.md) を参照してください。

### 開始方法

- **初回アクセス**：`index.html` を開くと自動的にウェルカム画面が表示されます
  （「3分デモを開始」または「自由に画面を見る」を選択）。2回目以降のアクセスでは表示されません。
- **URLから直接開始**：`?demo=1` を付けてアクセスすると、一度見たことがある場合でも
  必ずウェルカム画面が表示されます（LP・Instagram等からの直接誘導を想定）。
  既存のハッシュルーティングと共存できるため、`#/dashboard` を続けて付けても構いません。

直接開始URL（例）：

```
https://mkenta0717.github.io/contractor-compliance-mock/?demo=1
https://mkenta0717.github.io/contractor-compliance-mock/?demo=1#/dashboard
```

ローカルで確認する場合は `http://localhost:8080/index.html?demo=1` のようにアクセスしてください。

### 6ステップの概要

| STEP | 内容 |
|---|---|
| 1 | ダッシュボード →「○○ビル新築工事」を開き、不足を確認 |
| 2 | 「対応が必要」の山田太郎の行から不足資料を依頼 |
| 3 | 作業員側の提出画面をそのまま体験（サンプル資格証で提出可） |
| 4 | 通知から届いた資格証を確認 |
| 5 | 登録して不足解消・準備率100%を確認 |
| 6 | 提出資料を準備して完了 |

各ステップでは対象のボタン・行を枠＋背景でハイライトし、吹き出しに
「説明」と「次に何を押すか」だけを表示します（長文説明・スライド送りはありません）。
画面下部に固定表示される進捗バーから、いつでも「デモを終了」できます。

### 通常モードとの違い

- 通常モードは従来どおり自由に操作できます（デモは強制されません）。
- デモ開始時のみ `Store.reset()` 相当の初期化に加え、会社の「労災保険資料」を
  準備済み扱いにします（2〜4分程度に収めるための調整で、`js/data.js` の
  `SEED_DATA`（通常モードの初期データ）自体は変更していません）。
- デモ中はシナリオが崩れないよう、サイドバーの画面遷移を一時的に無効化します
  （「デモを終了」すると即座に元へ戻ります）。

### 作業員側の提出体験

デモ中に表示される「作業員側の提出を体験」ボタンを押すと、既存の `mobile-submit.html` を
`iframe` でそのまま呼び出します（別タブに遷移してユーザーが迷子にならないようにするため）。
PCでは375px幅相当のスマホフレームで中央表示、スマホでは全画面表示に切り替わります。
UI・ロジックは通常モード（シナリオD）と共通で、埋め込み時のみ「管理画面へ戻る」ボタンが
追加表示されます（URLの `embedded=1` パラメータで判定）。

### feedback / イベントログ

完了モーダルは、ガイド（スポットライト・進捗バー）を終了したうえで表示されます。
「もう一度体験する」「自由に画面を見る」は最初から選べ、下部の2つの質問（利用意向・価格受容度）
への回答は任意です（未回答のまま閉じても通常モードへ戻れます）。回答した場合のみ、以下のキーで
`localStorage` に保存されます（現時点では外部送信・バックエンド保存は行いません）。

| キー | 内容 |
|---|---|
| `teishutsu_demo_feedback_v1` | 完了時刻・利用意向（useIntent）・価格受容度（priceIntent）・所要秒数 |
| `teishutsu_demo_events_v1` | `demo_started` 〜 `demo_completed` 等のイベントログ配列（`recordDemoEvent()` に集約。将来、外部Analyticsへ置き換えやすくするための土台） |
| `teishutsu_demo_seen_v1` | ウェルカム画面を表示済みかどうかのフラグ |

## このサービスの位置づけ（重要）

このモックは「資格管理システム」ではなく、**複数の元請・複数の提出方式に対応する「提出準備アシスタント」** として設計しています。
現場詳細・提出資料生成の各画面で、元請ごとの「提出先」「提出方式（GreenSite / Buildee / Excel / PDF / メール等）」
「適用テンプレート」を必ず表示し、資格管理だけのツールと混同されないようにしています。
なお、GreenSite・Buildee等へは実際には一切接続していません（詳細は下記「未実装・意図的に行っていないこと」を参照）。

## 資格・教育の期限管理について

実務との齟齬を避けるため、資格・教育マスタには `deadlineType`（期限管理区分）を持たせています。

| 区分 | 表示ラベル | 挙動 |
|---|---|---|
| `none` | 期限なし | 一度取得すれば無期限（玉掛け・高所作業車・フルハーネス・足場・アーク溶接など）。期限警告の対象にしない |
| `legal` | 有効期限 | 法令上の有効期限があるもの。期限切れ・期限接近を判定する（現在のダミーデータでは未使用、区分としてのみ実装） |
| `recommendedTraining` | 次回教育推奨日 | 法定失効はないが再教育が推奨されるもの（職長・安全衛生責任者教育など）。**「資格失効」「期限切れ」とは表示せず**、常に「再教育推奨」という非ブロッキングな注意喚起にとどめる |
| `clientRule` | 元請確認期限 | 元請が独自に定める確認期限（区分としてのみ実装） |
| `companyRule` | 自社確認期限 | 自社が独自に定める確認期限（区分としてのみ実装） |

ダッシュボードのKPIも「期限切れ／30日以内に期限」ではなく「要対応／30日以内の確認」という、
実態を誤解させない表現にしています。

## 操作できる主要シナリオ

### シナリオA：不足資料を依頼する
ダッシュボード →「対応が必要な現場」の「○○ビル新築工事」行を開く → 現場詳細の「対応が必要」表で
山田太郎「高所作業車運転技能講習」が！未登録になっているのを確認 → その行の「依頼」（または上部の
「不足資料をまとめて依頼」）→ 内容を確認して「依頼を送信」→ 送信完了画面から
「作業員側の受け取り画面をプレビュー」で `mobile-submit.html` を確認できます。
送信後、対応が必要な表の該当行は「依頼済み」バッジ表示に変わります。

### シナリオB：AIで資格証を登録し、現場の不足が解消される
作業員管理 →「山田 太郎」を開く →「資格証を登録」→ 資格証画像をアップロード（サンプル資格証でも体験可）→
「資格証から情報を読み取っています…」の疑似処理のあと、抽出結果（氏名・資格名・発行機関・修了証番号・取得日・期限）が
フォームに自動入力されます。期限欄のラベルは資格名（`deadlineType`）に応じて「有効期限」「次回教育推奨日」等に自動で切り替わります。
内容を確認して「登録」を押すと資格が登録されます。
その後「○○ビル新築工事」の現場詳細に戻ると、「対応が必要」表から山田太郎の行が消え、
「作業員別提出状況」の状態も「要対応」→「完了」に変わり、準備率も上昇します。

### シナリオC：全書類が揃い、提出資料を生成する
シナリオBに加えて、会社情報ページの「労災保険資料」を（ダミーファイルで）アップロードすると、
「○○ビル新築工事」の準備率が100%になります。現場詳細の「提出資料を準備する」→ 提出資料生成画面で
「提出資料を準備する」を押すと、疑似的な生成処理のあと、元請（ABC建設株式会社）の提出方式（GreenSite＋独自Excel）に
合わせた内容一覧（GreenSite入力用確認一覧・独自提出シート・資格証一式・会社証明書一式・チェックリストなど）が表示されます。

### シナリオD：作業員からの資料提出を確認する
現場詳細 →「不足資料をまとめて依頼」→ 依頼送信完了画面の「作業員側の受け取り画面をプレビュー」から `mobile-submit.html` を開く
（実運用ではメール・SMSのリンクとして届く想定）→ 写真を撮る／ファイルを選択 →「提出する」。

作業員側の提出内容は `localStorage` を介して管理画面と疑似連動します。管理画面（別タブで開いたまま）を見ていると、
ベルの通知やダッシュボードの「新着・対応事項」に **「山田 太郎さんから高所作業車運転技能講習の資格証が届きました」**
という通知が自動で表示されます（ページを再読み込みしなくても、ブラウザの`storage`イベントで即座に反映されます）。

通知をクリックすると、シナリオBと同じ資格証登録の確認モーダルが開きます（提出された画像がプレビューされます）。
内容を確認して「登録」を押すと、資格として登録され、現場の不足状態が解消されます
（作業員が提出しただけでは即座に「有効」にはならず、必ず事務担当の確認・登録を経る、という業務フローを再現しています）。

※シナリオDは、ブラウザの2つのタブで「管理画面（index.html）」と「作業員側提出画面（mobile-submit.html）」を
同時に開いておくと、通知がリアルタイムで反映される様子までデモできます。

上記4シナリオは Playwright による自動操作で一連の流れが問題なく動作することを確認済みです
（コンソールエラー・ページエラーともに0件）。

## モックであるため未実装・意図的に行っていないこと

- 実際のデータベース・API・認証は一切なし（状態はブラウザの `localStorage` のみ）
- AI資格証読み取りは疑似処理（実際のOCR/AI APIは呼び出しません。読み取り結果はダミー生成です）
- メール・SMS送信は行われません（「送信しました」は疑似表示です）
- 提出資料のZIP生成は疑似表示のみで、実際のファイルダウンロードはできません
- GreenSite / Buildee との直接連携なし（提出前の「準備」を効率化する位置づけで、既存サービスの置き換えは行いません。
  画面上も「GreenSiteへ自動登録しました」等の誤解を招く表現は使わず、「GreenSite入力用データを準備」のように表記しています）
- 作業員側のスマホ提出画面で選択した写真は、その端末（ブラウザ）の `localStorage` に保存されるのみで、
  実際にどこかへアップロードされるわけではありません（管理画面との連動もあくまで同一ブラウザ内での疑似再現です）
- 現場・作業員・元請の新規登録、会社情報・元請情報・資格証の編集、元請テンプレートの新規作成・編集はモック対象外
  （「新規現場登録」「新規作業員登録」「新規元請登録」「編集」「プラン変更」等のボタンは、押すと
  「モック版では○○できません」という案内トーストが表示されるだけで、画面遷移はしません）
- ログイン・権限管理・工程管理・施工写真・チャット・勤怠・給与・請求・電子契約・KY・入退場管理・CCUS連携・
  施工体制台帳・健康診断結果・マイナンバー等の情報は一切扱いません（詳細は `MOCK_FEEDBACK.md` の対象外事項を参照）

## ダミーデータについて

登場する会社名・人物名・現場名はすべて架空のものです（株式会社三和設備、山田太郎 他）。
資格の有効期限・現場の提出期限などは、モックを開いた時点の端末の日付を基準に
「あと◯日」等の表示が動的に計算されます。そのため、閲覧するタイミングによって
ダッシュボードの件数や「残り◯日」の表示は変動します。

## デモを繰り返す場合

「設定」画面の下部にある「デモデータをリセット」ボタンで、いつでも初期状態に戻せます
（シナリオDで作業員側から提出した未確認の提出情報も、あわせてクリアされます）。
別の会社にデモを見せる前などにご利用ください。

### localStorageのスキーマについて

ダミーデータの構造（`templates` / `clients[].submissionMethods` / `certTypes[].deadlineType` など）を
変更した際は、`js/store.js` の `STORAGE_KEY` と `CURRENT_SCHEMA_VERSION`、および `js/data.js` の
`SEED_DATA.meta.schemaVersion` をあわせて更新してください。こうしておくことで、
古いスキーマの保存データが残っているブラウザで開いても、そのデータを使わず自動的に
最新のダミーデータで再初期化されます（`Store.init()` が起動時に検証します）。
